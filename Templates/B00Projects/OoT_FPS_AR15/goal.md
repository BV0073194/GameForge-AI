# Project Goal

Modify The Legend of Zelda: Ocarina of Time for Nintendo 64 using the current public zeldaret/oot decomp so it becomes a first-person-shooter-style playable experience centered initially on the user's uploaded AR-15. The AR-15 must be discoverable in Link's House, in the room where a new game begins, as a visible pickup that Link can collect immediately. The weapon must then become actually usable with the most technically appropriate implementation for the target: first-person/aiming behavior, firing, hit detection/damage, ammunition/reload behavior where appropriate, UI feedback, effects/audio using original or properly licensed/generated content, and save/load persistence.

Use the uploaded AR-15 model as source material, but do not blindly insert it unchanged. Analyze the current OoT/N64 rendering and asset pipeline, comparable in-game object/weapon art, hardware constraints, geometry budgets, texture formats/resolutions, materials, scale, animation requirements, collision, and performance. Create an optimized/stylized derivative that preserves the weapon's recognizability while looking natural in OoT's original visual style and running within realistic N64-era constraints.

Deep-research the current zeldaret/oot source, ZeldaRET documentation/resources, public N64/OoT modding tools, current asset/scene/object formats, public reverse-engineering documentation, emulator behavior, proven public examples, and any other authorized public technical source needed. Establish a reproducible clean base build before making gameplay changes. Verify the actual current scene/actor/object representations for Link's House rather than relying on stale tutorials. Work incrementally: first clean build, then pickup proof in Link's starting room, then collection, then held/equipped rendering, then aiming/firing, then damage/ammo/UI/save behavior, then polish.

Build the ROM/output locally using the user's legally obtained supported base input, launch it in an emulator, use emulator/runtime logs, crash data, OpenCV/game-window analysis, screenshots, process/freeze detection, scripted/recorded inputs, and regression tests. Preserve the vanilla starting sequence and unrelated gameplay unless the user's requested FPS design intentionally changes it. If a new feature breaks an existing required system, repair or roll back. Continue researching, implementing, building, booting, visually checking, playtesting, debugging, and repairing until the requested playable result passes the acceptance criteria or a genuine technical blocker is documented.
